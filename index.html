Abstract

Say what you want computed.

TWAIN turns a natural-language research request — “predict the aqueous solubility of aspirin at 25 °C” — into a planned, executed and validated computational-chemistry run on Washington University’s RIS cluster.

The hard part of computational chemistry is rarely the arithmetic. It is choosing a defensible method, sizing the job, writing an input deck without a silent unit error, getting it through the scheduler, and then knowing whether the number that comes back is right. TWAIN does that work as an explicit state machine and shows its reasoning at every step. You name a property and a system in plain English; naming the method, the engine and the basis set is its job, and it tells you what it chose before anything runs.

It is deliberately not an oracle. A run asks when the request is genuinely ambiguous, stops for human approval before it spends a core-hour, states in advance what result it would accept, and reports honestly when the answer misses that bar rather than presenting a number with no verdict attached.

The idea

A stop, not a notification.

Agentic systems tend to ask forgiveness. TWAIN asks permission, at the one moment where permission is meaningful: after it knows what it intends to do and what that will cost, and before any of it happens. The gate is enforced in the state machine’s transition table, not merely surfaced in the interface.

What you approve

The plan is a document you can edit, not a summary you acknowledge.

  • The method. Which library and engine, and why — including any substitution it had to make because the tool it wanted is not installed here. TWAIN only ever plans with tools it can actually import, and it says so when that changed the plan.
  • The resources. CPUs, GPUs, RAM and wall time, each seeded with TWAIN’s suggestion and each editable. Every field states the cluster’s real ceiling, and an over-ask is clamped rather than becoming a job the scheduler will never run.
  • The acceptance bar. The value and tolerance the result will be judged against, stated before the run — so the verdict cannot be reverse-engineered from whatever came back.
  • The cost. Estimated model spend and core-hours, up front.

How it works

Eleven stages, and a run that can wait.

A run is a state machine, not a prompt chain. When it needs a human — a clarification, the plan approval, a confirmation before an expensive calculation — it suspends: the state is checkpointed to Postgres and the process released, so nothing sits pinned waiting on a person. A reply enqueues a resume job and the run picks up where it was.

Understand

INTAKE parses the request into a structured spec. CLARIFY asks about only the fields intake left uncertain — bounded, so it cannot interrogate you indefinitely. DECOMPOSE builds a goal graph and rejects one that is cyclic.

Plan

DISCOVER scores catalogued tools against the request and keeps only those actually installed here. PLAN commits to a toolset, sizes the job, and writes the acceptance bar.

Run

BUILD generates a self-contained run bundle, which is statically checked and smoke-run before it goes anywhere. EXECUTE runs it — locally, in a container, or submitted to Slurm on RIS.

Judge

INTERPRET extracts metrics from stdout and output files. VALIDATE grades them. ACCEPT puts the result in front of you. TERMINATE closes the run.

Trust

Knowing when the answer is wrong.

A number from a solver is not a result. TWAIN checks its work in three independent places, because the failure modes are different and any single check catches only one of them.

Before it runs

A static pass over the generated script — does it compile, does it have an entrypoint, does it reference the calculator, are all names defined — plus a smoke run, with real errors fed back for self-correction.

Against the literature

Metrics are compared to a baseline database and graded into accepted, needs review, or rejected. Where no baseline covers the system, the plan’s own acceptance criteria are the reference — and where there is no reference at all, the report says so rather than inventing a verdict.

Against physics

A magnitude backstop checks the result against known physical ranges for that property and unit. It exists for the error that agrees with itself all the way through — a conversion applied twice, arriving two orders of magnitude out and looking perfectly plausible.

A rejected result routes back to planning; one that needs review is diagnosed and corrected. Both loops are bounded and every stop carries a reason, so a run cannot quietly spend another allocation trying to argue with the same answer.

Where it runs

Real engines, on a real cluster.

Runs execute on WashU RIS (compute2) through Slurm, in per-engine environments provisioned on team storage. The registry catalogues ten calculator engines and seventeen curated tools; these are the engines currently provisioned as environments:

  • Psi4 quantum chemistry
  • GPAW DFT — plane-wave / LCAO
  • NWChem quantum chemistry
  • CP2K DFT, molecular dynamics
  • ABINIT plane-wave DFT
  • Quantum ESPRESSO plane-wave DFT
  • DFTB+ tight binding

Status

Where the project actually is.

TWAIN is a research prototype under active development, not a finished product. The pipeline — intake through planning, code generation, execution on Slurm, result parsing, validation and self-correction — is built and tested. The governance layer and the end-to-end chemistry benchmark are still in progress.

The deployed web app is limited to institutional sign-in with a WUSTL Key and is not open to the public. If you would like to see it, the source is on GitHub and runs locally with a single command.
